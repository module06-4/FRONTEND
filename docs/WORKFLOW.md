# 0. Z는 무엇을 하는 서비스인가

Z는 회의를 대체하지 않는다. 회의는 회사에서 오프라인으로 진행되고, Z의 역할은 그 내용을 사람이 일일이 정리해서 전달하는 수작업을 없애는 것이다.

> **"회의를 녹음해서 제출하면, AI가 내용을 분석해 담당자별 액션으로 자동 분배한다."**

이 원리가 조직 구조를 타고 반복된다.

- **프로젝트** (Owner 개설)
  - **프로젝트 회의** (Owner 주최 · 참석자: 각 팀장) → AI 분배 →
    - **팀 액션** (팀별 생성, 팀당 여러 개 가능)
      - **팀 액션 회의** (Leader/Member 주최 · 참석자: 팀원) → AI 분배 →
        - **개인 액션** (팀원별 생성)

모든 액션·회의·프로젝트는 태그로 연결되어, 화면 어디서든 태그를 클릭하면 상위·하위로 끊김 없이 이동한다. 이게 Z를 "자료·문서 관리형 그룹웨어"로 만드는 핵심이다. 또 하나의 축은 **인수인계** — 휴직·퇴사 시 액션을 재분배하고 승인 라인을 타고 올라가는 흐름이다.

**온보딩은 4단계다** — 팀 체계 → 직급/권한 → 사원 초대 → **결제**. 결제를 마쳐야 워크스페이스가 열린다(2026-08-04, 무료 요금제·체험 없음).

**기본 역할은 Owner / Leader / Member 3종.** Admin은 별도 역할이 아니라 Owner가 누구에게든 부여할 수 있는 부가 권한 플래그다 (자세한 내용은 9절).

### 공통 상태값 (전면 통일)

- ⚠️ **범위는 프로젝트·팀 액션·개인 액션 셋뿐이다.** 회의는 별개 생애주기(`SCHEDULED`/`IN_PROGRESS`/`DONE`/`CANCELED`, §3-2)를 쓴다 — "완료 여부"가 아니라 "지금 어느 단계인가"를 말하는 값이라 아래 3상태로 못 맞춘다(2026-08-16 명시 — "전면 통일"만 읽고 회의 상태까지 3개로 줄이려 들지 않는다).
- **실제로 저장하는 값은 "완료 여부"(`isDone`) 하나뿐이다**(2026-08-07 확정, 2026-08-16 문서 정정 — 예전 판이 "할일/진행중/완료 3개를 저장한다"로 잘못 적어 뒀었다). "할일"·"진행중"은 시작일·마감일·오늘로 **항상 계산**한다(저장 안 함): `오늘<시작일→할일` / `시작일≤오늘≤마감일→진행중`, **"지연"도 계산**한다(마감일로, 진행중 칸 안의 배지). 시스템은 "실제로 착수했는지"를 모른다 — 알 필요가 없다, 오늘이 시작일을 지났으면 그냥 진행중이다.
  상태 필드에 넣으면 마감일과 두 벌이 되어 반드시 어긋난다(CLAUDE.md §도메인 상수). (기존 "대기"는 "할일"로 통일, **"리뷰" 상태는 전면 폐기** — 코드의 상태 타입·색상 매핑·범례·배지 어디에도 "리뷰"가 남아있으면 안 됨)
- 상태색: 할일=회색 / 진행중=초록 / 완료=보라 / 지연=빨강.
- ⚠️ **보드 드래그가 실제로 바꾸는 값은 "상태"가 아니다**(2026-08-16 재확정 — 8절 참고). 할일→진행중 드래그는 상태를 직접 정하는 게 아니라 **시작일을 오늘로 세팅**하는 것뿐이고, 그 뒤로 진행중 여부는 계속 날짜로 계산된다. **진행중↔완료만 사람이 직접 토글하는 진짜 상태값**(`isDone`)이다.

### 페르소나 계정 (더미 데이터 기준)

- **박대표** — Owner (팀 없음, 사원 관리에서 팀 컬럼 "-"로 표시)
- **김서준** — 개발팀 Leader
- **이하윤, 박도현** — 개발팀 Member
- **최유진** — 마케팅팀 Leader / **정민석, 임지안** — 마케팅팀 Member
- **강서연** — 디자인팀 Leader / **한소율** — 디자인팀 Member
- **오현우** — 전략기획팀 Leader
- 좌측 하단 계정 표시는 현재 로그인/역할 전환에 따라 이 페르소나로 동기화된다 (Owner→박대표, Leader→김서준, Member→이하윤).
- 대표 프로젝트 3개: **연예인 굿즈 쇼핑몰 앱 구축(GOODS, 개발·마케팅·디자인)**, **3분기 마케팅 브랜드 리뉴얼(BRAND, 마케팅·디자인)**, **사내 협업툴 리뉴얼(COLLAB, 개발·전략기획)**.

# 1. 프로젝트

**정의**: 여러 팀이 함께 참여하는 최상위 작업 단위. 예: "연예인 굿즈 쇼핑몰 앱 구축". 팀 하나짜리 이니셔티브는 프로젝트가 아니다.

### 생성 — `/app/projects/new`

- **Owner만** 생성 가능.
- 입력: 프로젝트명 · ProjectTag(프로젝트당 1개 고정, 영문 대문자만·최대 6자) · 세부 설명 · **태그 색상(다크모드 대응 고정 팔레트 11색 중 선택 — 자유 HEX 아님)** · **시작일** · 마감 기한 · 참여 팀 지정(다중) · 첨부파일(기획서 PDF 등).
  ⚠️ **시작일은 사용자가 직접 입력하고, 그 값이 최초 상태를 정한다**(2026-08-16 확정 — 액션과 같은 계산 규칙, §0). 시작일이 미래면 "할일"로, 오늘이거나 과거면 "진행중"으로 생성 즉시 계산된다. **보드에서 할일→진행중으로 드래그하면 이 시작일이 오늘로 덮어써진다**(§8의 액션과 완전히 같은 동작 — 미리 입력해 둔 미래 시작일이 있어도, 드래그 순간 "지금 착수했다"는 오늘 날짜로 갱신된다). 마감 기한보다 늦을 수 없게 달력 min/max로 제한한다.

### 목록 — `/app/projects`

- **전 구성원 조회 가능.**
- 필터 탭 3개: **할일 / 진행중 / 완료**.
- 마감 임박순 정렬(오름차순) + 페이지네이션.
- 카드 라벨: **프로젝트명 · 프로젝트 태그 · 담당 팀(3개까지 라벨, 4개 이상이면 "+N", hover 시 전체 — 2026-08-10에 2개에서 3개로 올림, `project/lib.ts`의 `MAX_VISIBLE_DEPARTMENTS`) · 진척율(%) · 마감일 · 상태**. 임의 KPI 탭·지연 태그 없음.
  ⚠️ **진척율 = 해당 프로젝트 태그가 달린 개인 액션(리프 노드)의 완료율**(2026-08-16 확정). 팀 액션은 세지 않는다 — 팀 액션 자체가 그 하위 개인 액션 완료 비율로 파생되는 값이라(§4, `childDoneCount`/`childTotalCount`), 팀 액션과 개인 액션을 둘 다 더하면 같은 완료가 두 번 카운트된다.

### 상세 — `/app/projects/:projectId`

- 탭 2개: **기획** / **타임라인**
- **기획 탭**: 전 구성원 조회 가능 (수정·첨부파일 교체는 Owner만). 게시글형(프로젝트명·기획 상세·태그·마감·첨부파일 다운로드).
- **타임라인 탭**: 이 프로젝트의 **여러 팀의 팀 액션이 하나의 통합 타임라인에** 함께 보인다 (팀 탭으로 쪼개지 않음). 타임라인 디자인 규칙은 11절 참고.
  - **팀 액션 1개 = 좌측 라벨(팀명) 1개 + 막대 1개인 독립된 한 행이다**(2026-08-16 코드 대조 정정 — "팀 박스"·"같은 팀은 같은 색·인접 배치"는 실제로 없다, 11절 참고). 팀명 라벨은 전부 같은 회색이고 그룹핑 구조도 없다.
- 브레드크럼: "프로젝트명" 단독 표시.

# 2. 프로젝트 회의 (Owner 주최)

**정의**: 프로젝트에 참여하는 각 팀의 팀장들을 모아, 프로젝트를 팀별 작업(팀 액션)으로 쪼개는 회의. 3절(회의 공통 기능)을 따르되 Host가 Owner라는 점에서 아래 특이사항이 있다.

- **개설**: `/app/rooms`에서 시간대 예약과 동시에 진행. **Host가 Owner이므로 "프로젝트 태그" 선택만 필수**, "상위 팀 액션" 필드는 뜨지 않는다(계층 최상단).
- **참석자**: 프로젝트 참여 각 팀의 팀장들. ⚠️ **팀장만 지정 가능하도록 강제한다**(2026-08-13 확정, FE #452) — 참석자 피커에 "전체" 옵션이 없고 항상 팀장급으로만 좁혀진다(서버 재검증 포함). 회의록에서 이름이 불린 사람이 곧 그 팀의 대표라는 게 이 제한으로 확정되고, 그게 아래 팀 액션 배분의 전제가 된다.
- **캡처**: Host(Owner) 전용.
- **AI 분배 결과 = 팀 액션.** ⚠️ **AI는 발화 텍스트로 부서를 추론하지 않는다**(2026-08-13 확정 — 틀렸을 때 검토 화면에 고칠 자리가 없으면 조용히 잘못된 팀에 하달된다). 대신 검토 화면(`/app/meeting/:id/review`)에서 "담당자" 자리가 **"부서" 선택**으로 바뀌고, 리뷰어(Owner)가 각 액션마다 부서를 직접 골라야 [액션 분배 확정]이 풀린다. 부서 옵션은 이 회의 참석자(=팀장들)에서 만든다(참석자 목록 자체가 팀별 대표 목록이라 별도 팀 조회 없이 구성). 회의 상세에 이 회의에서 하달된 **팀 액션 목록**이 산출물로 표시된다 (각 행: 팀 액션명·담당 팀명·상태·마감일, 클릭 시 팀 액션 상세로 이동). ↔ 팀 액션 회의는 개인 액션 목록을 보여주는 것과 대칭.
  - 담당 팀장 이름은 팀 액션 어디서도 저장하지 않고 **그때그때 조회**한다(그 팀의 현재 팀장이 바뀌어도 팀 액션 자체는 그대로이므로).
  - ⚠️ **팀장이 공석인 팀은 이 회의의 부서 옵션에 안 뜬다**(2026-08-16 확정). 참석자가 팀장으로만 좁혀지는데(위 항목) 공석 팀은 참석자로 세울 사람이 없기 때문 — 그 팀에는 신규 팀장이 지정될 때까지 새 팀 액션을 못 준다. 공석 해소는 §9(팀장 승격)·§7(오프보딩 귀속)을 따른다.
- **회의 라벨**: Host가 Owner인 회의는 **"Owner 개설"** 라벨을 단다 (기존 "프로젝트 공통" 문구는 폐기). Host가 Owner가 아닌 회의에는 이 라벨 대신 "상위 팀 액션 · OOO" 라벨만.
- **열람 권한**: 참석 팀장 + Owner. ⚠️ **추적 체인 보완**: 참석자가 아니어도 이 회의에서 자기 팀에 팀 액션이 하달됐다면 그 팀장은 이 회의를 열람할 수 있다(출처 회의 추적 단절 방지).

# 3. 회의 공통 기능 (회의실 예약, 캡처, AI 리뷰)

### 3-1. 회의실 예약 = 회의 개설 (통합 기능) — `/app/rooms`

- 회의실 예약과 회의 개설은 **하나의 모달**. 캘린더 빈 시간대 선택 = 회의 개설. **30분 단위 한 타임**(2026-08-05 확정 — 연속 예약으로 늘리지 않는다), **즉시 확정**(승인 없음).
  ⚠️ **[미결] 녹음이 예약 시간을 넘기는 경우의 처리는 아직 안 정했다**(2026-08-16). 캡처(§3-3)는 녹음 시간에 제한이 없어, 30분 예약을 넘겨 녹음하면 다음 예약자와 시간이 겹친다 — 막을지, 자동 종료할지, 겹침을 그냥 둘지 결정 전이라 지금은 둘 다 그대로 둔다.
- 모달 입력: 시간대 · 회의실 · 참석자 · **회의 제목** · **회의 안건(대주제/소주제** — **자유 입력 텍스트 인풋**, 대주제 1개+소주제 1개 필수, 나머지 "추가/삭제" 버튼으로 인풋 늘리고 줄임) · **프로젝트 태그**(필수) · **상위 팀 액션**(조건부).
- **상위 팀 액션 노출 조건 — Host 역할 기준**:
  - Host가 **Owner**: 필드 안 뜸. 프로젝트 태그만 (= 프로젝트 회의).
  - Host가 **Leader/Member**: 프로젝트 태그 선택 후, 그 프로젝트 내 **자기 팀에 하달된 팀 액션** 중 하나를 반드시 선택해야 예약 완료 (= 팀 액션 회의). 한 팀이 팀 액션을 여러 개 가질 수 있어 이 지정으로 구분.
- 선택된 프로젝트 태그·상위 팀 액션은 회의와 그로부터 파생되는 모든 액션에 자동 상속.
- `/app/meeting`(회의 목록)과 **모든 대시보드**에는 "새 회의 만들기" 버튼/모달이 **없다** — 회의 개설(대면·비대면 모두) 진입점은 `/app/rooms` 하나뿐이다(2026-08-14 사이드바 개편, `meeting/page.tsx` 주석 확인). 비대면 회의(3-1-A)도 회의실·시간대를 안 쓸 뿐 진입점은 같은 화면(회의실 목록 패널의 별도 버튼)이다 — `/app/meeting` 목록에는 그리로 가는 이동 링크만 있다.

### 3-1-A. 비대면(온라인) 회의 — 외부 회의 녹음 제출 (2026-08-13 확정)

**정의**: 다른 회사·외부에서 이미 끝난 회의를 녹음해 온 뒤, 그 녹음 파일을 통째로 제출해 AI 요약·분배만 돌리는 경로. 3-1(실시간 캡처: 예약→녹음→종료)과는 성격이 다르다 — **이미 벌어진 일을 사후 기록**하는 것이지 지금부터 회의를 시작하는 게 아니다. 네이밍 미정, 문서에서는 "비대면 회의"로 통칭.

- **진입점**: `/app/rooms`(회의실 예약, 위 3-1과 같은 화면)의 회의실 목록 패널에 있는 [비대면 회의] 버튼(2026-08-16 정정 — `/app/meeting`이 아니다, 2026-08-14 사이드바 개편으로 회의 개설 진입점이 전부 `/app/rooms`로 모였다). 예약 모달과는 별개의 신규 모달.
- **모달 입력**: 예약 모달(3-1)과 동일한 필드(참석자·회의 제목·안건·프로젝트 태그·상위 팀 액션 조건부)에서 **회의실·시간대 선택을 빼고, 녹음 파일 첨부**를 더한다. 파일 업로드·처리 방식은 BE·FE 모두 검토 중(별도 이슈).
- **참석자**: 규칙은 3-1과 완전히 동일하다 — Owner 개설이면 팀장만, Leader/Member 개설이면 자기 팀만(2절 "팀장만 지정 가능하도록 강제한다" 참고). **새 모달이라고 다른 규칙을 쓰지 않는다.**
  - 회의에 실제로는 타사(외부) 인원이 있었어도 그 사람은 참석자로 못 잡는다(우리 시스템에 계정이 없음) — 별도 표현 없이, 그 발화의 담당자를 AI가 특정 못 하면 기존과 같은 **"담당자 미정"**으로 넘어가 검토 화면에서 사람이 채운다.
- **상태**: 제출 즉시 `DONE`으로 확정된다. `SCHEDULED`·`IN_PROGRESS`도, `/capture` 화면(3-3)도 거치지 않는다. 회의실 슬롯을 소비하지 않으므로 `/app/rooms` 캘린더에는 뜨지 않는다(즉시 완료 상태라 "예정된 회의"가 아니다).
- **일정**: `startAt`·`endAt`은 사용자가 입력하지 않고 DB에도 저장하지 않는다(nullable). 회의 목록·상세 어디서도 시간 범위를 안 그리고, **"온라인으로 진행된 회의입니다"** 안내 문구로 대신한다 — 발화 기록(3-2 "스크립트") 자리도 동일한 문구로 대체한다(실시간 캡처가 아니라 화자 귀속 근거인 자막 청크 자체가 없다).
  - 목록 정렬 기준(시간 없는 회의를 어디에 둘지)은 BE가 정한다.
- **알림**: 개설 알림도 시작 10분 전 알림(10절)도 없다 — 이미 끝난 회의의 사후 제출이라 "곧 시작한다"는 전제 자체가 성립하지 않는다.
- **AI 분배 결과**: 2절·5절 규칙을 그대로 따른다 — Owner가 올린 비대면 회의도 **팀 액션 후보**(검토 화면 부서 선택 포함), 그 외엔 개인 액션.

### 3-2. 회의 열람 — `/app/meeting`

- 필터 탭 2개: 내가 개설한 / 참여해야 할.
- **예정·진행중 카드는 클릭해도 반응 없다**(2026-08-16 정정 — "진행중은 상세로 들어간다"가 아니다, `meetingCardAffordanceOf`의 `live` 판정이 예정·진행중 둘 다를 묶는다). 회의가 끝나기 전까지는 정리된 내용(발화 기록·산출물)이 없어 상세로 보낼 게 없다 — Host든 Attendee든 카드 몸통 클릭은 똑같이 무반응이고, **Host에게만** 발치의 **[녹음하기]** 버튼(아래 항목)이 별도로 뜬다. **완료 카드만** 클릭 시 상세(회의 내용·참석자 명단·ProjectTag·전체 스크립트, 화자 구분 없이 청크 단위) 진입.
  ⚠️ **무반응이어도 조용히 안 되는 척 하지 않는다**(CLAUDE.md §정직성). 클릭 시 아무 동작 없이 넘어가면 고장으로 읽힌다 — 커서를 `default`로 두거나, hover 시 "회의가 끝나면 회의록이 열립니다" 툴팁을 붙인다.
  - ⚠️ **완료 카드에도 예외가 하나 있다.** 요약이 끝났는데(`REVIEWED`) Host가 검토 화면에서 **[액션 분배 확정]** 을 아직 누르지 않았으면 그 자리는 **[액션 검토]**(`/app/meeting/:id/review`)가 가져간다 — 검토가 밀리면 액션이 아무에게도 안 가므로 회의록보다 급하다. 판정은 `meetingCardAffordanceOf` 한 곳이 한다.
- Host는 **예정·진행중** 회의에 **[녹음하기]** 버튼이 시간 제약 없이 노출 → `/app/meeting/:id/capture`.
  - ⚠️ **"입장"이라 부르지 않는다**(2026-08-11 개명). 이 버튼은 캡처 화면으로 옮겨 주는 링크일 뿐 서버를 부르지 않는다 — "입장"이라 부르니 회의에 들어가는 별도 단계가 있는 것처럼 읽혔고, 백엔드의 입장 API(`POST /api/v1/meetings/:id/entry`)가 상태를 바꾸는 자리로 오해될 소지가 있었다. **회의가 실제로 시작되는 순간은 캡처 화면의 [녹음 시작] 하나다.**
  - ⚠️ **진행중에도 뜬다.** 녹음 중 새로고침·크래시로 화면을 잃었을 때 목록이 유일한 복귀 입구다.
- **회의 상세 라벨**: 임의 해시태그(#OKR 등) 노출 안 함. **프로젝트 태그(필수)**, 팀 회의면 **상위 팀 액션 라벨**, Owner 개설 회의면 **"Owner 개설"** 라벨, 그리고 **회의 안건(대주제/소주제)**은 별도 섹션 유지.
- **참석자 명단 수정**(2026-08-12 확정, MEET-09): 상세의 참석자 섹션에 host에게만 [참석자 수정] 링크가 뜬다. 예약 모달의 참석자 피커(`RoomAttendeePicker`)를 그대로 재사용하는 다이얼로그에서 명단을 **전체 교체**한다(부분 추가·삭제 아님). **회의가 SCHEDULED·IN_PROGRESS일 때만** 뜬다 — DONE이면 안 보인다. host는 서버가 자동 포함·제거 불가로 처리한다.
- **회의 취소**(2026-08-13 확정, MEET-06): 상세 머리글(제목 옆)에 host에게만 [회의 취소] 버튼이 뜬다. **SCHEDULED(시작 전)일 때만** 뜬다 — IN_PROGRESS·DONE은 취소가 아니라 종료(MEET-08, 캡처 화면)를 쓴다. 확인 창에서 [회의 취소]를 누르면 소프트 취소(`CANCELED` 상태, 물리 삭제 아님)되고 예약 슬롯이 풀린다. 목록 카드는 `취소` 배지만 뜨고 [녹음하기]·[회의록] 모두 안 보인다(다시 열 방법이 없다).
- **발화 기록(스크립트)**: 회의마다 그 회의 주제에 맞는 개별 스크립트를 가진다 (모든 회의가 공용 더미 스크립트를 재사용하지 않음).

### 3-2-1. 열람 권한 — **목록과 상세는 다르다** (2026-08-06 확정)

⚠️ **목록 조회(제목·어느 팀·어느 프로젝트 하위인지)와 상세 조회(발화 기록·산출물 등 내용)는 권한이 다르다.** 이 구분이 특히 **통합검색**에서 중요하다 — 검색 결과엔 회의가 걸릴 수 있지만, 결과에 뜬다고 그 내용까지 열 수 있는 건 아니다.

- **목록**: 제목·소속 팀·프로젝트 태그 등 메타 정보는 **전 구성원 공개**(통합검색 결과 포함). 권한 없는 회의도 카드는 보이되, 눌러도 상세로 못 들어간다.
- **상세(내용 — 발화 기록·산출물 등)**: 아래 매트릭스로 막는다(`lib/permission.ts` `canViewMeetingDetail`).
  - **Member**: **자신이 참석자로 지정된 회의만.** 타 팀 또는 Owner가 개설한 회의는 참석자가 아니면 **아예 열람 불가**.
  - **Leader**: **자신의 팀 내에서 이루어진 회의** + **Owner가 개설한 회의**(참석자가 아니어도 전부 허용) + 본인이 참석자인 회의. **타 팀 회의 내용은 열람 불가**.
  - **Owner**: **전체 열람 가능**.
  - 액션 상세의 "출처 회의" 링크를 권한 없는 사람이 보면 에러 대신 **잠금 아이콘 + "참석자만 열람 가능" 툴팁**.

### 3-3. 캡처 — `/app/meeting/:id/capture`

- **Host 전용.** Attendee용 캡처 레이아웃 없음. 타이핑 메모 없음(폐기).
- **첫 화면은 "녹음 준비"**(가운데 한 장) — 회의 메타·참석자와 브라우저·마이크 지원 여부를 보여 주고 **[준비 완료]** 로 작업 화면을 연다. **서버를 부르지 않는다**(상태 전환 아님). 버튼만 두면 누르는 순간 마이크 권한 창이 떠서 무슨 일인지 모른 채 거부하게 되므로, 무엇이 시작되고 무엇이 아직 아닌지 먼저 적는다.
- **버튼 2계열**:
  - **[녹음 시작]** → 누르면 **[일시정지]/[재개] 토글**로 바뀜
  - **[회의 종료 및 제출]** → 녹음 시작 후 활성. (기존 "녹음 중지/파일 제출/종료"를 하나로 통합)
- 중단: 실시간 자막(문장=청크 단위) + 참가자 목록.
- **STT**: 녹음 시작과 동시에 STT 시작. 브라우저 STT는 정적 3~4초면 세션이 끊기므로 `onend`→`start` 자동 재시작 루프로 "끊김 없이 듣는 것처럼" 처리(별도 마이크 버튼 없음, 데스크톱 기준). 필요 시 STT 계층만 상용 STT로 교체 가능하게 분리.
- **녹음/파일 기술**: 프론트 `getUserMedia`+`MediaRecorder`. **10분마다 완결 독립 파일**을 만들려면 `timeslice`(조각이 독립 재생 불가)가 아니라 **`stop→start` 구간 재녹음(segment) 방식** 사용. 여기에 더해 **`recorder.start(15000)`으로 15초 조각도 함께 흘려보낸다**(크래시 시 유실을 10분→15초로 줄이기 위한 절충 — 백엔드 확정). 세그먼트는 그대로 10분마다 끊고, 서버가 세그먼트 닫힐 때 그 안의 15초 조각들을 concat해 10분 완결 파일을 만든다.
- **일시정지**: 녹음·STT 둘 다 멈춤. 파일은 안 쪼갬 — 재개 시 정적 구간 빠진 하나의 연속 파일로 이어짐(MediaRecorder pause/resume 스펙 보장·검증 완료). **10분 카운트는 일시정지 제외 "실제 녹음 누적 시간" 기준.** 일시정지 구간 오디오 파일 별도 전송 없음(단, 상태 이벤트는 서버에 알림 — 아래 참고).
- ⚠️ **회의 중 서버가 하는 일은 "받아쓰기(STT) + 파일 적재"까지만.** 요약·주제 분류·액션 추출은 **전부 회의 종료 후**에 한다. (이유: "10:03 제가 할게요 → 10:15 김대리가"처럼 뒤 발언이 앞을 뒤집는 경우, 회의 중에 요약·분류를 확정하면 되돌릴 수 없음 — 앞 계층이 정한 걸 뒤에서 못 고치는 원칙. 받아쓰기는 뒤집힐 게 없으므로 회의 중 허용.)
- **흐름 & API 시점 (백엔드 확정본)**:
  1. **[녹음 시작]/[일시정지]/[재개]** → 각각 **상태 이벤트 API 호출**(회의 도메인 CAP-01/02/03). 오디오 파일은 안 보내지만 상태는 반드시 알린다. 서버가 이걸 알아야 ⓐ시간 기준점(`startedAtEpochMs`) 발급 ⓑ참석자 STT 트리거 ⓒ새로고침 복구(`/captures/active`) ⓓ녹음자 점유·이어받기 ⓔ녹음 없던 구간 기록이 가능.
  2. STT 청크(문장) 생성 때마다 → **자막 청크 전송 API**. 서버는 **받아서 쌓아두기만** 함(회의 중 주제 분류·요약 안 함).
  3. 15초마다 → **조각 업로드 API** / 실제 누적 10분(세그먼트 닫힘)마다 → 서버가 조각 concat해 **10분 완결 파일 확정**. 서버는 **적재만** 함(구간 사전 요약 안 함).
  4. **[회의 종료 및 제출]** → 확인 모달("회의를 종료하고 요약을 진행하시겠습니까?") → **종료 알림 API**(마지막 세그먼트 확정 포함) + 회의 DONE. **AI 분석은 프론트가 호출하지 않는다** — 서버가 종료 처리 안에서 자동으로 분석 잡을 큐에 걸고, 실패해도 서버가 재시도(사용자가 창을 닫아도 안전).
  5. AI 분석 진행 표시(2026-08-13 정정 — 숫자 진행률 아님): `GET /api/meetings/:id/processing-status`(CAP-06)는 퍼센트를 안 준다 — 전체 상태 4단계(`NOT_STARTED`/`RUNNING`/`DONE`/`FAILED`)와 계층(`layers[]`)별 enum뿐이다(숫자 진행값은 STT 구간에만 있고 그마저도 화면엔 안 씀). 그래서 화면은 **스피너 + "요약 중이에요" 정도의 단계 표시**만 한다(진행률 바 아님).
  6. **완료·실패는 알림 SSE로 안다**(`ANALYSIS_COMPLETED`/`ANALYSIS_FAILED`, 10절) — 개설자에게만 push된다. 화면 우측 하단 지속형 카드가 스피너 → 완료/실패로 그 자리에서 바뀌고, 완료 카드를 누르면 리뷰 화면으로 이동한다(닫기 전까진 화면을 옮겨도 유지). "완료 뱃지"는 이 카드와 회의 목록 카드 상태 전환을 함께 가리키는 말이다.
- **종료 정책**: [회의 종료 및 제출]은 되돌릴 수 없다 — 마지막 파일 제출+분석 시작이 묶여 있어, **종료 후 재녹음 불가**(다시 하려면 회의를 새로 개설). 일시정지(보조 버튼)와 종료(강조/위험색)를 시각적으로 명확히 구분.
- **화면 관점 요약**: 위 API·서버 동작은 전부 연동 로직이라 **캡처 화면 UI(버튼 2계열·실시간 자막·확인 모달·스피너+단계 안내)는 변동 없음.**
  - ⚠️ CAP-06(`GET /api/meetings/:id/processing-status`)의 `status`(`NOT_STARTED`/`RUNNING`/`DONE`/`FAILED`)와 회의 목록의 `AI_SUMMARY_STATUS`(`PENDING`/`SUMMARIZING`/`REVIEWED`/`DISTRIBUTED`/`FAILED`)는 **서로 다른 계약**이다 — 이름이 비슷해 헷갈리지 않게 구분한다. 화면이 실제로 쓰는 값은 CAP-06 응답의 `status` 하나뿐이고, `layers[]`는 지금 프론트 액션이 넘겨받지 않는다.

### 3-4. AI 리뷰 — `/app/meeting/:id/review`

- 완료 뱃지 클릭으로 진입. **Host만 접근.**
- **두 그룹은 시각적 구분(라벨)일 뿐, 수정은 전부 가능 (A안)**: "AI 확신도 높음"과 "AI 요약 불확실" 둘 다 담당자·시작일·마감일·내용을 자유롭게 수정할 수 있다(확신도 높음 그룹도 잠그지 않음). 이유: AI가 내용 확신도는 높아도 이름/담당자를 잘못 알아듣는 케이스가 있어 확신도 높음도 손볼 수 있어야 함(백엔드 협의). ⚠️ 시작일은 2026-08-07 팀 확정(보드·프로젝트 상태 계산이 시작일을 쓰므로 액션도 동일 정책).
  - 섹션 제목은 차이가 드러나게: **"AI 확신도 높음 N건"**(검토 안 해도 되지만 할 수 있음) / **"AI 요약 불확실 N건"**(봐주세요). "확정 전 검토 가능"은 화면 상단 안내로 한 번만.
  - **"자동 반영 완료" 로직 폐기** — 확신도 높음이든 확인 필요든 실제 **하달**은 **[액션 분배 확정] 한 번**으로 통일(둘 다 확정 시점에 함께 하달).
    ⚠️ **"생성"이 아니라 "하달"이다**(2026-08-16 확정 — 예전엔 "확정 시점에 함께 생성"으로 적어 아래 `actionsConfirmed` 서술과 어긋났다). **AI가 뽑은 액션 행은 회의 종료 직후 분석 단계에서 이미 만들어져 있다** — 확정·하달 전이라 담당자 화면에 안 나타날 뿐이지 행 자체는 이미 있다. [액션 분배 확정]이 하는 일은 그 행을 **내보내는 것**이다.
    - 이 버튼에서 세 갈래가 갈린다: ① **수정 사항 유무와 무관하게** 확정·하달 ② **반려(✕)** 한 항목은 하달되지 않음 ③ **[액션 직접 추가]** 로 넣은 항목은 확정 시점에 함께 확정·하달.
- **근거 발화(evidence) 표시 (필수)**: 각 액션 행 아래에 그 액션이 도출된 회의 발화를 한 줄로 표시한다. 예: `💬 "A/B 테스트 도구는 서준님이 비교해서 정리해주세요"  ▶ 21:24`. 발화 텍스트 + 시각(+화자). 수정 판단의 근거이므로 반드시 있어야 함.
- **마감일 기본값**: AI가 뽑은 마감일이 각 액션의 날짜 칸에 기본으로 채워져 있어야 한다(사용자가 전부 손입력하면 자동화 의미 없음).
  ⚠️ AI가 **안 집으면 프로젝트 마감일**이 기본값이다(2026-08-05 확정). 어느 쪽이든
  **[액션 분배 확정] 시점의 값이 최종**이고, 그 뒤로 자동으로 바뀌지 않는다.
- **Owner 회의는 "담당자" 대신 "부서"를 고른다**(2026-08-13 확정, 2절 참고). 화면 상단에 안내 배너 한 번(행마다 반복 안 함), 각 액션 행의 담당자 드롭다운이 부서 드롭다운으로 바뀐다. [액션 직접 추가]도 같은 모드를 따른다 — 담당자 대신 부서를 고른다. 부서·담당자는 상호 배타(둘 다 채운 상태로 확정 불가, BE가 422로 막음).
- **수동 추가**: "확인 필요" 목록 하단 **[액션 직접 추가]** 버튼 — 담당자(또는 부서)·내용·마감일 직접 입력. 수동 항목도 [확정] 시 함께 **하달**되고 이 회의·상위 팀 액션·프로젝트 태그를 상속.
- **반려(✕)**: 각 액션 행 오른쪽 ✕ 버튼으로 잘못 뽑힌 액션을 제외할 수 있다. ✕ 클릭 시 사유 5택(2026-08-12 BE 실코드 대조로 정정 — 3택 아님): **HALLUCINATION**(그런 말 한 적 없음) / **DUPLICATE**(중복) / **NOT_ACTION**(액션이 아님) / **NOT_ATTENDANCE**(참석자 발화가 아님) / **ETC**(기타). 반려 액션은 [확정] 시 생성 대상에서 제외. (담당자·날짜만 고친 경우는 사유를 BE가 필드 기준으로 자동 유도한다 — MODIFY는 사유를 안 보낸다, ✕ 반려할 때만 사람이 사유를 고른다.)
- Host가 조정 후 **[액션 분배 확정]** → 담당자·확정 내용으로 액션 **하달** API(위 참고 — 행은 이미 있고 이 호출이 내보낸다).
- ⚠️ **1회성 화면 정책**: 확정된(또는 회의가 완료되어 액션이 생성된) 회의의 `/review` 접근 시 회의 상세(`/app/meeting/:id`)로 리다이렉트, 재진입 불가. 확정 산출물은 회의 상세에 남으므로 정보 손실 없음. (구현: `actionsConfirmed` 플래그, 확정 시 true.)
  ⚠️ **정본은 `actionsConfirmed`(= BE `dispatchedAt !== null`) 하나뿐이다**(2026-08-16 명시). `AI_SUMMARY_STATUS.DISTRIBUTED`는 값만 선언돼 있고 실제로는 안 쓴다(확정 전·후를 그 값으로 가르는 로직이 없다) — 나중에 그 구분이 필요해지면 `actionsConfirmed`를 지우지 말고 `DISTRIBUTED`를 그 파생값으로 연결한다, 별도로 두 값을 각자 저장하지 않는다.
  ⚠️ **[알려진 한계] Host가 확정 전에 퇴사(오프보딩)하면 그 회의의 AI 초안은 확정할 방법이 없다**(2026-08-16 — 이 화면이 Host 전용·재진입 불가라 대체 경로가 없음, 리뷰어가 인지한 문제이나 지금은 범위 밖). 발생 빈도를 보고 별도 이슈로 다룬다.
- FAILED → [다시 요약하기] (재분석 요청만, 파일 선적재되어 재제출 불필요).

# 4. 팀 액션

**정의**: 프로젝트 회의 AI 분배로 특정 팀에게 생성되는 작업 단위. **한 팀이 한 프로젝트 안에서 여러 개** 가질 수 있다.

### 목록 — Leader 개인화: `/team/action`

- **로그인 Leader의 소속 팀의 팀 액션만** 표시. 프로젝트별로 그룹핑하되 그룹 안엔 자기 팀 것만.
- **타임라인 좌측의 반복되는 팀 박스 열은 없다** — 이미 자기 팀만 보는 화면이라 불필요. 대신 각 프로젝트 그룹 위에 그룹 헤더("프로젝트명 · 태그 · N개 팀 액션")만 유지하고, 그 아래 팀 액션 막대들이 바로 나열된다.

### 목록 — 공개 진입: 프로젝트 상세 타임라인 탭

- 프로젝트 상세 타임라인에서 다른 팀의 팀 액션도 함께 보임. 클릭 시 공개 상세 라우트 `/app/projects/:projectId/team/:teamActionId`로 이동 — Leader 목록에서 진입하는 상세와 **같은 데이터·같은 컴포넌트** 재사용.

### 상세 — `/app/projects/:projectId/team/:teamActionId`

- 이 화면은 특정 팀 액션 하나로 이미 진입한 상태다. **좌측의 팀 그룹 박스는 없다.**
- 상단: 팀 액션명(크게) · 소속 팀명 · 상태 · 마감 · 상위 프로젝트 기획 첨부파일 다운로드(참조 상속, 복제 아님).
- 타임라인: 이 팀 액션에 속한 **개인 액션들을 담당자별 행으로** 표시. 각 행 좌측에 **[원형 아바타] 담당자 이름 (역할)** — Leader면 "(개발팀장)", Member면 본인 역할 라벨("(프론트엔드)"), 없으면 이름만. 좌측 담당자 영역 폭은 화면의 20~25%로 제한.
- 개인 액션 막대 클릭 시 그 개인 액션 상세(`/app/actions/:id`)로 이동.

### 조회 권한

- **전 구성원 공개.** 다른 팀의 팀 액션도 프로젝트 상세를 거쳐 열람 가능.

### 상태 변경

- 상세엔 상태 변경 UI 없음. 상태 변경은 **보드에서만** (8절).

# 5. 팀 액션 회의 (Leader/Member 주최)

**정의**: 팀 액션을 팀원들에게 나눠 개인 액션으로 쪼개는 회의. 3절 공통 기능을 따르되 Host가 Owner가 아니라는 점에서:

- **개설**: `/app/rooms`에서 프로젝트 태그 + **상위 팀 액션 선택 필수**. ⚠️ **개설자는 Leader뿐 아니라 Member도 될 수 있다**(2026-08-16 명시 — 이 회의는 "리더가 여는 회의"가 아니라 "그 팀 액션을 받은 팀의 누구든 열 수 있는 회의"다).
- **참석자**: 개설자가 **그 팀 소속 전원(팀장 포함) 중에서 골라서 지정**한다(2026-08-16 명시 — 팀원 전체 자동 포함이 아니다, 그리고 팀장도 후보에서 빠지지 않는다). 다만 후보 범위는 그 팀 소속으로 제한된다(3-1-A의 "자기 팀만"과 같은 범위 제한 규칙).
- **AI 분배 결과 = 개인 액션.** 회의 상세에 이 회의에서 나온 **개인 액션 목록**이 산출물로 표시.
- 팀장 본인이 Host이면서 그 액션 담당자가 되는 경우 → 예외 없이 일반 흐름과 동일.
- ⚠️ **팀장 공석 중에도 이 회의는 열 수 있다**(2026-08-16 명시, §2와 대조). 이미 그 팀에 하달된 팀 액션이 있으면 팀원 아무나 개설자가 될 수 있어 공석과 무관하다 — 막히는 건 §2(Owner의 프로젝트 회의가 그 팀에 **새** 팀 액션을 배분하는 것)뿐이다.

# 7. 인수인계서

**정의**: 휴직·퇴사(오프보딩) 시 보유 액션 재분배 흐름. Owner 제외 전 역할 신청 가능.

### 신청 — `/app/handover`

- 본인 담당 액션 전체 리스트.
- 토글: **휴직 / 오프보딩.** ⚠️ **Leader도 둘 다 신청 가능**.
- **휴직**: 시작일·종료일 달력 2개 + 인수인계 액션 선택.
- **오프보딩**: 전체 액션 자동 선택(해제 불가) + **"담당 업무 및 인수인계 상세 설명" 자유 텍스트 입력란**.
- [인수인계서 생성] → 완료 모달.

### 팀원(Member) 처리 — `/team/handover`, `/team/handover/:id`

- 목록: 인수인계서명 · 담당자 · 휴직/오프보딩 · (휴직 시) 기간.
- 상세 **레이아웃(2026-08-09 정정)**: **상단 = 신청자 인계 액션 타임라인**(공용 타임라인 컴포넌트 재사용 — 둥근 상태색 막대+막대 안 텍스트+오늘 실선+월/주 헤더, 단순 리스트 아님, 읽기 전용) + 우측 상단 "PDF 다운로드". **하단 = "배정할 액션" 목록**(액션 한 줄마다 담당자 `<Select>`). ⚠️ **드래그 앤 드롭·별도 팀원 보드는 없다**(원래는 팀원별 드롭 칼럼에 드래그하는 구조였으나, 배정한 항목이 목록에도 그대로 남아 보여 어디에 배정됐는지 헷갈리는 문제로 제거 — `<Select>` 하나로 배정 상태를 표현).
- "N/M건 배정 완료" 카운터 + [인수인계 확정] 버튼(모든 액션 배정 시 활성) + **[반려]** 버튼(항상 활성). 액션 클릭 시 액션 상세로 이동.
- [인수인계 확정] → 재할당 + **휴직/오프보딩 중간 승인 자동 처리**.
- **[반려]** — 팀장도 반려할 수 있다(오너의 최종 승인/반려와 별개). 인계 액션이 빠졌거나 잘못 배정된 걸 팀장 선에서 걸러내려는 목적. 클릭하면 사유 입력 모달이 뜨고, 확인하면 신청이 되돌아가 신청자가 재직 상태로 복귀한다(오너의 반려와 같은 결과).
  ⚠️ **신청 중(팀장 중간 승인 대기~오너 최종 승인 대기) 상태의 이름은 `MEMBER_STATUS.WAITING`이다**(2026-08-16 명시 — 이미 구현돼 있던 값, 문서 누락이었을 뿐). 사원 관리 목록(§9)의 "상태" 컬럼에 이 값이 뜬다.
  ⚠️ **팀장·오너의 승인/반려는 알림으로 안 알린다**(2026-08-16 확정 — 의도된 설계). 신청자는 `/app/handover`에 다시 들어가 직접 확인한다.
- ⚠️ PDF 다운로드는 **오프보딩만** 둔다. 휴직은 돌아올 사람이라 이 화면의 배정이 임시 기록이지만, 오프보딩은 퇴사 뒤 남는 유일한 인수인계 문서라 보관용 PDF가 필요하다.
- ⚠️ **중간 단계는 팀장 몫이다 — Owner·Admin 대행은 두지 않는다**(2026-08-16 확정). 팀장이 자리를 비웠을 때 대신 승인하게 하려면 이 화면(팀장이 팀원 인수인계서를 관리하는 자리)을 그 두 역할에게도 열어야 하는데, 범위에 비해 중요도가 낮다 — **향후 개선**으로 남긴다.

### 최종 승인 (일반 팀원) — `/manage/members/:id`

- **Owner 전용**(2026-08-06 확정: Admin 제외)이 "팀장 중간 승인 완료" 표시만 확인 후 **최종 승인/반려**. 실무 내용 직접 볼 필요 없음.
  ⚠️ 화면(`/manage/members`) 자체는 Admin도 들어간다(계정 발급·직급 변경은 그대로 Admin 가능) — **[최종 승인/반려] 버튼만** Owner에게만 보인다. 화면 접근과 승인 액션의 권한이 갈린다.
- ⚠️ **오프보딩 최종 승인 = 즉시 소프트 삭제다**(CLAUDE.md §도메인 상수, 2026-08-15 정정 — "최종 승인 후에만 탈퇴 가능"이 아니라 승인 그 자체가 탈퇴 처리다). 별도의 "탈퇴" 액션이 남아 있는 게 아니다.

### 팀장(Leader) 본인 휴직 — 자가 선택적 재할당 → 사원 관리에서 최종 승인

- 팀장 위엔 상위 리더가 없으므로 본인이 신청+재할당을 동시에 처리한다.
- `/app/handover`에서 휴직 선택 시: 본인 개인 액션(**팀 액션은 대상 아님**) 중 **휴직 기간에 넘길 것만 선택적으로** 고르고, 각 액션에 팀원 담당자를 직접 지정. (팀장 개인 액션도 팀 액션 안에서 분배받은 것이라 재할당 권한 문제 없음. 권한이 걸리면 본인이 인수인계 대상에서 빼면 됨 → 선택적 인수인계.)
- [인수인계 확정] → 재할당 즉시 반영 + 중간 검토 단계 없이 **곧바로 Owner의 사원 관리 최종 승인 대기**.
- **Owner만**(2026-08-06 확정: Admin 제외) **사원 관리 탭(`/manage/members`)에서 일반 사원과 동일하게 [휴직 최종 승인]**. ⚠️ **팀장 휴직은 오너용 "팀장급 인수인계서 관리(`/owner/leader-handovers`)" 페이지에 올라오지 않는다** — 그 페이지는 오프보딩 전용. 오너가 휴직 인수인계서 내용을 따로 열어볼 필요 없이 승인만 하면 됨.
- 복귀 시 되돌려받는 로직 없음 — 재할당 순간 영구 귀속(액션 얘기다, 계정 상태는 아래 참고).
- ⚠️ **계정 상태(재직/휴직)는 휴직 종료일이 지나면 자동으로 재직으로 전환된다**(2026-08-16 확정 — 별도로 사람이 승인 버튼을 누르지 않는다). 신청 시점에 이미 종료일이 정해져 있어서 사람이 개입할 이유가 없다.
  ⚠️ **경계는 "종료일까지 휴직"이다**(2026-08-16 확정). 종료일이 8/20이면 **8/20까지 휴직, 8/21부터 재직**이다 — 종료일 당일을 재직으로 세지 않는다. 하루 차이가 배포 뒤 데이터로 굳으므로 구현 전에 이 기준을 먼저 맞춘다.

### 팀장(Leader) 본인 오프보딩 — 보류함 → 신규 리더 재귀속

- 일반 팀원과 동일 흐름, `/team/handover` 없이 곧바로 Owner.
- Owner PDF 확인 후 **[오프보딩 최종 승인]** → 계정 퇴사 처리 + 인수인계서 **"귀속 대기"**. 그 팀의 **팀 액션은 팀 소속이라 그대로 유지**(다른 팀으로 안 넘어감). **리더 공석 중에도 새 팀 액션 하달·회의 개설은 막히지 않음** — 회의 개설 조건은 "본인이 그 팀 소속인가"만 보지 "현재 리더가 있는가"는 안 봄. 별도 예외 처리 불필요.
  - 단, 보드의 "팀 액션" 탭은 Leader 뷰라 새 리더 지정 전까지 그 팀의 팀 액션 모아보기 뷰만 잠시 없을 수 있음(각자 "내 액션"으로 본인 몫 확인 가능하니 업무 흐름은 안 막힘).
- Owner가 새 팀장을 정하고(먼저 "직급·권한 변경"으로 Leader 승격) **`/owner/leader-handovers`**(팀장급 인수인계서 관리함)에서 그 인수인계서를 열어 **[이 인수인계서를 OOO에게 귀속]** → 개인 액션 전체 일괄 이전, "귀속 완료"로 전환.
- **`/owner/leader-handovers` 페이지에는 오프보딩 인수인계서만 올라온다**(팀장 휴직은 안 올라옴 — 위 참고). 목록: 인수인계서명·퇴사 팀장·팀·오프보딩 승인일, 필터: 귀속 대기 / 귀속 완료. 상세: 담긴 액션 전체 + PDF 다운로드 + 수신자 선택(이미 Leader로 승격된 사원 중) + [OOO에게 귀속]. **접근 권한 Owner 전용**(CLAUDE.md §라우트 그룹과 동일 — Admin도 결국 팀장급이라 다른 팀장의 오프보딩을 승인하는 건 위계상 성립하지 않는다).

# 8. 보드 — `/app/board`

**정의**: 3열(할일/진행중/완료) 드래그 앤 드롭 화면. 조회·추적은 각 상세 페이지 몫.
⚠️ **드래그가 "상태를 바꾸는" 게 아니다**(2026-08-16 정정, §0 참고). 할일→진행중 드래그는 **시작일을 오늘로 세팅**하는 것뿐이고, 그 뒤로 그 칸에 있을지는 계속 날짜로 계산된다. **진행중↔완료(`isDone`)만 사람이 직접 토글하는 진짜 상태 변경**이다 — 그래서 허용된 드래그 전이도 **할일→진행중 · 진행중→완료 · 완료→진행중** 세 가지뿐이고, 할일↔완료 직행이나 진행중→할일은 막는다(화면·서버 액션 양쪽에서 재검증).

### 역할별 대상

| 역할   | 보이는 것                                                                                                                                                                                                                          |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner  | 프로젝트 카드 (단일 목록) — 프로젝트명·태그·마감일(또는 지연 배지)만. 참여 팀·완료율 바·팀/개인 액션 수는 없다. 카드는 **드래그 전용이라 클릭해도 상세로 안 간다**(`board-card.tsx` 주석 "옮기는 화면이지 이동하는 화면이 아니다") |
| Leader | 개인 액션 카드 (단일 목록) — **Member와 완전히 같다**                                                                                                                                                                              |
| Member | 개인 액션 카드 (단일 목록)                                                                                                                                                                                                         |

⚠️ **"Leader 전용 팀 액션 탭"은 없다**(2026-08-16 코드 대조 정정 — 예전엔 탭 2개로 적었지만, `BoardType`은 `"project" | "my-action"` 둘뿐이고 Leader도 Member와 똑같이 `my-action` 보드만 받는다). 팀장이 자기 팀 팀 액션 진척을 보는 자리는 `/team/action`(4절)이지 이 보드가 아니다.

### 저장 방식

- **낙관적 UI + 즉시 저장**(#686, 2026-08-24 변경). 드래그·[옮기기] 버튼으로 놓는 순간 화면을 먼저 바꾸고, 백그라운드로 서버 액션(`commitBoardChangesAction`)을 부른다 — 이동 하나당 요청 하나. 실패했을 때만 원위치로 되돌리고 실패 토스트를 낸다. 성공했을 때는 별도 토스트를 안 낸다(화면이 이미 옮겨진 자리를 보여 주고 있어 소음이다).
- ⚠️ **예전엔 배치 저장이었다**(폐기 — [저장하기] 버튼 + 확인창 + 미저장 이탈 방지). 확인창이 흐름을 끊는데도 브라우저 크래시·강제 종료엔 무력해 이동이 유실될 수 있었다 — 즉시 저장이 유실 위험도 없애고 확인 단계도 없앤다. `overrides`·[저장하기] 버튼·`BoardLeaveGuard`·`BOARD_SAVE_HINT`·`BOARD_REVERT_LABEL`가 이때 함께 사라졌다.
- ⚠️ **진척율(%)과 완료 토글은 서로 다른 축이다**(2026-08-16 명시). 진척율은 하위 액션 완료 비율의 자동 계산값(§1)이고, 프로젝트 카드의 완료 여부는 Owner가 이 화면에서 직접 토글하는 값이다 — 진척율 100%여도 Owner가 아직 완료로 안 옮겼으면 그 프로젝트는 계속 "진행중"으로 계산된다(문서화·QA 승인 등 남은 일이 있을 수 있어서다). 자동으로 맞추지 않는다.

# 9. 관리자 권한(Admin) — 부가 권한 플래그

- Admin은 4번째 역할이 **아니다.** Owner가 임의 사원에게 `is_admin = true`를 부여하면 **기존 역할 유지한 채** 사이드바에 관리자 메뉴 추가 노출.
  - > ⚠️ **위 Figma 메모는 낡았다**(2026-08-16 정리 — 코드 대조 결과 "역할 전환 드롭다운"에 해당하는 화면 기능이 지금 코드에 없다. 과거에 있던 개발용 미리보기 토글(`?as=member|leader`, `BoardRolePreview` 등)은 이미 완전히 제거됐다 — `member-table.tsx`가 실제로 권한 배지·Admin 배지를 분리해서 그린다, 아래 참고). 실제 Figma를 다시 확인해 정말 남아 있으면 그때 새로 기록한다.
- `is_admin` 접근 화면: 계정 발급(사원 관리 화면 안 버튼으로 여는 모달 — 전용 라우트 없음, 아래 참고. Leader·Member만 발급 대상) · 사원 관리(`/manage/members`) · 직급·권한 변경 · **구독·결제** · **용량 관리**. (구독·결제·용량 관리 화면은 Owner 전용에서 "Owner 또는 is_admin" 접근으로 확장 — 화면 내용은 동일 재사용.)
  ⚠️ **회의실 관리(`/manage/rooms`)는 여기 안 든다 — `is_admin` 전용이고 Owner 단독은 안 된다**(2026-08-16 확정, 다른 관리 화면과 다른 의도된 예외). `canManageRooms`(`lib/permission.ts`)는 다른 관리 화면(`canManageMembers`·`canManageBilling`·`canManageStorage`, 전부 "Owner 또는 is_admin")과 달리 **`is_admin`만 본다** — Owner가 관리자를 겸직하지 않았으면 이 화면에 들어가도 [등록]·[수정] 버튼이 안 보인다. 회의실 관리는 Owner가 직접 할 필요 없는 잡무로 보고 처음부터 빼기로 한 팀 결정이다.
  ⚠️ **인수인계 최종 승인 · 사내 공지 작성은 Admin 접근 화면 목록에서 뺐다**(2026-08-06). 사원 관리·공지 화면 자체는 계속 Admin도 들어가지만(계정 발급·직급 변경, 공지 열람), **그 안의 승인 버튼·작성 버튼만 Owner 전용**이다 — 화면 접근과 개별 액션 권한이 갈리는 사례다.
  ⚠️ **계정 발급은 이제 Owner도 한다**(2026-08-06). ⚠️ **전용 라우트는 없다**(2026-08-16 코드 대조 정정 — 예전엔 "`/manage/new`에서 `/manage/members/new`로 옮겼다"고 적었지만, `account-issue-dialog.tsx` 주석에 "전용 라우트를 두지 않는다 — 목록에서 하는 일이라 목록을 떠나지 않는다"로 명시돼 있고 실제로 그 경로 파일이 없다). 사원 관리(`/manage/members`) 화면 안 버튼을 누르면 그 자리에서 모달이 뜬다. 화면 접근 권한(Owner·Admin 공통)과 발급 권한이 같은 문이라 별도 판정 함수를 두지 않는다.
- `/manage/*` 라우트는 "역할 === admin"이 아니라 **"is_admin === true"** 조건으로 접근 제어.
- ⚠️ **"관리자 권한 부여" 토글은 Owner 전용이다**(2026-08-16 코드 대조 정정 — 2026-08-05에 "Owner·is_admin 둘 다"로 바꿔 적었던 게 실제 코드와 반대였다). `canChangeAdminGrant`(`lib/permission.ts`)는 `role === OWNER`만 허용하고, BE 계약도 `hasRole('OWNER')`다 — 이미 겸직 중인 Admin이 다른 사람에게 겸직을 새로 주지는 못한다.

### 팀 구조와 "역할" 라벨

- 온보딩 팀 체계는 **팀(개발팀·디자인팀 등) 단위까지만 조직 계층**. 팀 아래 "프론트엔드/백엔드"는 **또 다른 계층이 아니라 그 팀원의 세부 역할 라벨**.
- 한 팀의 **Leader는 평상시 항상 1명**, 나머지는 Member. ⚠️ **단, 팀장 오프보딩 승인~신규 팀장 지정 사이는 공석이 정상 상태다**(2026-08-16 명시 — §7 "리더 공석 중에도 새 팀 액션 하달·회의 개설은 막히지 않음"과 이 문장이 어긋나 보이지 않게 범위를 함께 적는다. 실제로 2026-08-08에 이 공석을 못 다루던 순환 잠금 버그를 고친 이력이 있다). "프론트엔드/백엔드"는 각 팀원에게 하나씩(또는 없음) 붙이는 태그.

### 사원 관리 목록(`/manage/members`) 컬럼

- 컬럼: **이름 · 팀 · 직급 · 권한 · 역할 · 상태 · 입사일**
  - **권한**: Owner/Leader/Member 셋 중 하나(시스템 접근 권한). ⚠️ **Admin은 이 컬럼의 값이 아니다**(2026-08-16 정정 — 위에서 "4번째 역할이 아니다"라고 한 것과 같은 이유로 여기 나열하면 모순이다). `is_admin`이면 별도 배지를 권한 값 옆에 얹는다(`member-table.tsx`가 이미 이렇게 그린다) — Leader이면서 Admin인 사람은 "Leader" + Admin 배지로 함께 보인다.
  - **역할**: 팀 내 세부 역할 라벨(프론트엔드 등), 없으면 "없음"
  - Owner(박대표)의 팀은 "-"
- "미완료 액션" 컬럼 없음.

### 팀원 관리(`/team/members`) — 팀원 카드 아코디언

- 로그인 팀장의 팀원을 **접었다 펼치는 카드**로 표시(테이블 아님).
- **접힌 요약 행**: [원형 아바타] 이름 (역할) · 재직/휴직 뱃지 · 담당 액션 N개 · 진척도 바(그 팀원 개인 액션 완료율 %) · 우측 펼치기 chevron.
- **펼친 상세**: 그 팀원 개인 액션 리스트 — 각 행 [프로젝트 태그 · 상위 팀 액션명 · 개인 액션명 · 상태 · 마감일], 클릭 시 액션 상세로 이동.
- 상단 컨트롤: 정렬(담당 액션 많은 순 / 진척 낮은 순 / 지연 있는 순) + 필터(전체/재직/휴직).
- 팀원 ~6명 규모 가정, 접힌 카드가 한 화면에 다 보이게 컴팩트하게.

# 10. 알림 — 상단 배너 + 우측 하단 지속형 카드, 두 갈래(사이드바 알림 탭 폐기)

- 사이드바의 "알림" 탭/**화면**은 제거한다(`/app/notification` 라우트 없음).
  ⚠️ **스트림 자체는 남는다.** 알림은 SSE로 오고 BFF(`/api/notifications/stream`)가 토큰을 주입한다 —
  없앤 건 **보여주던 화면**이지 전달 경로가 아니다.
- ⚠️ **표현이 알림 종류에 따라 두 갈래로 갈린다**(2026-08-13 확정). BE `NotificationType`을 이 기준으로 나눈다:
  - **상단 배너**(화면 최상단 가로줄, 닫기(X) 가능, 일회성): `MEETING_CREATED` · `MEETING_REMINDER` · `MEETING_CANCELED` · `NOTICE_CREATED`.
    ⚠️ **`MEETING_ATTENDEE_ADDED`·`MEETING_ATTENDEE_REMOVED`는 아직 구현되지 않았다**(2026-08-16 코드 대조 정정 — 예전엔 "6종"이라 적혀 있었으나 `constants/notification.ts`의 `NOTIFICATION_TYPE`엔 실제로 위 4개뿐이다). 참석자 명단 수정(§3-2 MEET-09)이 알림까지 쏘는 건 아직 계획일 뿐 배선이 안 됐다 — 만들 때 이 두 값을 `NOTIFICATION_TYPE`에 추가하고 `event.ts`의 payload 스키마도 채운다.
  - **우측 하단 지속형 카드**(스피너 → 완료/실패로 그 자리에서 상태만 바뀌고, 닫기 전까지 화면을 옮겨도 유지): `ANALYSIS_COMPLETED` · `ANALYSIS_FAILED`(회의 종료 후 백그라운드 요약 완료·실패, **개설자에게만** 발송). 완료 카드를 누르면 그 회의 리뷰 화면(`/app/meeting/:id/review`)으로 이동한다. 이 두 알림은 회의 종료 시점의 1회성 토스트("백그라운드에서 요약 중입니다")를 대체한다 — 토스트는 몇 초 뒤 사라져서 그 뒤로 요약이 끝났는지 깨졌는지 알 방법이 없었다.
  - ⚠️ **개인 액션 하달·인수인계 승인/반려는 알림이 없다**(2026-08-16 확정 — 둘 다 의도된 설계). 액션을 받은 사람은 `/app/my/actions`나 보드에서 직접 확인해야 안다 — 하달 시점에 배너를 쏘는 기능은 지금 범위 밖이다. 인수인계 승인·반려도 마찬가지로 신청자가 `/app/handover`에 다시 들어가 상태를 봐야 한다.
- 상단 배너 발생 시점(2가지, 기존):
  1. **회의 개설 시** (참석자 전원 — 개설자 Host도 참석자이므로 포함).
  2. **회의 시작 10분 전** (참석자에게).
     ⚠️ **문구는 BE가 조립해서 그대로 준다**(2026-08-16 코드 대조 정정 — 예전엔 "[제목] 회의가 [장소]에서 [시간]시에 시작합니다. 늦지 않게 참석해 주세요" 같은 조립형 예시를 적어 뒀는데, 실제 계약은 그렇지 않다). FE는 `message`를 그대로 쓰고 장소·시각·안내 문구를 직접 조립하지 않는다(`event.ts` 주석: "message에 이미 제목이 들어 있다, BE가 `제목 + " 회의가 개설되었습니다."`로 만든다") — 실제 문구는 그보다 훨씬 단순하다.
- 회의 예약(개설) 확정 시 처리 순서: 예약 확정 → 회의실 캘린더를 revalidate(상태 갱신)해서 슬롯이 즉시 캘린더에 나타나게 함 + 동시에 위 1번 상단 배너 표시.
- **공지 생성 시**(전 구성원): `NOTICE_CREATED`도 위 상단 배너 4종 중 하나다 — 공지 등록 커밋 뒤 같은 회사 전체 구성원에게 상단 배너로 발행된다([확인] BE `NoticeCreatedNotificationTrigger` 대조, 2026-08-13). 배너와는 **별개로** 사이드바 "공지" 탭에도 새 공지가 있으면 **빨간 점 배지**가 뜨고, 해당 공지를 조회하면 배지만 사라진다(배너는 배너대로 닫아야 사라짐) — 둘은 같은 이벤트의 두 가지 다른 표현이다.

# 10-A. 기타 워크벤치 화면

### 회의실 — `/app/rooms` / `/manage/rooms`

- 회의실 데이터 필드: **이름 · 위치**뿐이다. (**"수용 인원" 필드는 전면 폐기** — 추가/수정 모달·목록·데이터 구조 어디에도 없음. **"이용 가능 시간"(운영시간) 필드도 폐기**(2026-08-15, BE PR #523 — DB 컬럼째 삭제) — 회의실은 이제 도메인상 항상 이용 가능하다, 예약 가능 시간대를 회의실별로 따로 두지 않는다.)
- `/app/rooms`(예약=개설): 캘린더 뷰. 캘린더 **우측에 "회의실 목록" 조회용 사이드바**(2026-08-10, 하단에서 이동 — 회의실 이름 · 위치, `/manage/rooms` 중앙 데이터를 그대로 읽음). 예약은 캘린더에서, 이 목록은 참고용.
- `/manage/rooms`(is_admin): 회의실 목록 + 추가/수정 모달(이름·위치). 예약 승인 절차 없음.

### 캘린더 — `/app/calendar`

- 월간 달력(그리드) 뷰.
- **개인 Todo**: 로그인 사용자가 특정 날짜에 자신의 Todo(제목+날짜)를 직접 추가, 그 날짜 칸에 표시(본인 소유, 타인에게 안 보임).
- **일정 표시(역할별)**: Member/Leader → 본인 개인 Todo + 본인 할당 개인 액션(마감일 기준). Owner → 개인 액션 대신 **자신이 개설한 프로젝트를 시작~마감 기간만큼 기간 막대로** 표시. (Todo와 액션/프로젝트는 시각적으로 구분)
- 데이터: 개인 액션은 로그인 사용자 담당분만 필터, 프로젝트는 전사 프로젝트 목록에서 가져온다.

### 공지 — `/app/notice` (단순 CRUD)

- **작성/수정/삭제 권한: Owner 전용**(2026-08-06 확정: Admin 제외 — 회사 대표가 전사에 알리는 공지라는 성격상 겸직으로는 안 연다). Leader·Member·Admin 겸직자 전원에게 관련 버튼 미노출. 열람(목록·상세)은 전 구성원.
- 작성: 목록 화면에 "공지 작성" 버튼(Owner만). 작성 폼은 **제목 + 내용 2필드만**.
- 수정/삭제: 버튼은 **상세 조회 화면에만** 둔다(목록엔 없음). Owner에게만. 삭제 시 확인 모달 → 확인 시 삭제 후 목록으로.

# 11. 타임라인 시각 디자인 규칙 (전 화면 공통)

프로젝트 상세·팀 액션 상세·`/team/action` 등 타임라인을 쓰는 모든 화면에 공통 적용.

- **막대**(2026-08-16 코드 대조 정정 — `action-timeline.tsx`, 예전 서술과 실제 구현이 셋 다 반대였다): 항목명은 막대 **바깥**(좌측 라벨 열)에 적고, 막대 **안쪽**에는 D-day 텍스트가 들어간다. 채움도 "꽉 채운" 색이 아니라 상태색의 옅은 투명도(10~12%) + 테두리 조합이다.
- **오늘 표시**: 점선이 아니라 차트 전체 높이를 관통하는 **끊기지 않는 실선**, 상단 끝에 "오늘" 라벨/점.
- **기간·상태 정합성**: 막대는 시작일~마감일 구간에 그린다. **진행중이면 막대가 반드시 "오늘" 선을 가로질러야** 한다. 할일=오늘 이후, 완료=오늘 이전, 진행중=오늘 포함.
  ⚠️ **이건 지켜야 할 규칙이 아니라 계산 결과다**(2026-08-16 명시 — §0·§8 참고). "진행중"은 애초에 "시작일≤오늘≤마감일"로 정의되는 계산값이라, 막대가 오늘 선을 가로지르지 않는 진행중 카드는 나올 수가 없다 — 상태를 사람이 임의로 골라 날짜와 어긋나게 둘 방법 자체가 없다.
- **월/주 날짜 헤더**: 상단 유지.
- ⚠️ **팀 색상 고정 매핑은 없다**(2026-08-16 코드 대조 정정). 프로젝트 상세 페이지 주석: "팀명은 무색이다 — 팔레트는 프로젝트 태그 전용". 팀명 라벨은 전부 같은 회색(`--muted`)이고, "같은 팀 박스가 인접 배치"되는 그룹핑 구조 자체가 없다 — 팀 액션마다 독립된 한 행일 뿐이다.
- **좌측 영역**: 화면마다 라벨 내용은 다르지만(프로젝트 상세는 팀명, 팀 액션 상세·`/team/action`은 담당자 이름(역할)), 폭은 **어디서나 고정 224px**다(`LABEL_COL_PX`, `action-timeline.tsx`) — "화면의 20~25%" 같은 비율이 아니다. 좌측에 별도 "팀 박스"를 그리는 화면은 없다.
- ⚠️ **원형 아바타는 없다**(2026-08-16 코드 대조 정정). 담당자 표기는 상태점(`StatusDot`류) + 텍스트 칩뿐이다 — 이니셜 아바타 컴포넌트가 어디에도 안 쓰인다. 뒤로가기는 고정 경로가 아니라 `navigate(-1)`(브라우저 이전 페이지)로 유지.

# 13. 페르소나 예시 플로우

등장인물: **박대표**(Owner) · **김서준**(개발팀장) · **이하윤**(개발팀원)

## 13-1. 프로젝트 개설 → 프로젝트 회의 → 팀 액션 하달

1. 박대표가 `/app/projects/new`에서 "연예인 굿즈 쇼핑몰 앱 구축"(GOODS, 개발·마케팅·디자인, 기획서 PDF 첨부) 생성.
2. `/app/rooms`에서 "8월 킥오프 미팅" 예약·개설. 참석자는 각 팀장. Owner라 프로젝트 태그만 선택 → 회의 상세에 "Owner 개설" 라벨.
3. 회의 당일 박대표(Host) 캡처: [시작]→녹음→[제출]→[종료]→백그라운드 분석.
4. 완료 뱃지 → 리뷰 화면. 확신 높은 항목도 손볼 수 있고, 확인 필요 항목을 조정(+필요 시 [액션 직접 추가]) 후 [액션 분배 확정]. 확정 후 이 리뷰 화면은 재진입 불가(회의 상세로 리다이렉트).
5. 개발팀에 "앱 개발 착수", 마케팅팀에 "TV 광고 계약 및 모델 섭외" 팀 액션 생성. 회의 상세에 이 팀 액션 목록이 산출물로 남음.

## 13-2. 팀 액션 회의 → 개인 액션 하달

1. 김서준이 `/team/action`에서 "앱 개발 착수" 확인 — 개요 탭에서 프로젝트 기획서 PDF도 다운로드 가능.
2. `/app/rooms`에서 "앱 개발 착수 - 기획 회의" 예약. Owner가 아니라 프로젝트 태그(GOODS)+상위 팀 액션("앱 개발 착수") 선택 필수. 참석자 개발팀 전원.
3. 캡처·분석 후 확정 → 이하윤에게 "온보딩 플로우 와이어프레임 검토" 등 개인 액션 하달. 회의 상세에 개인 액션 목록이 산출물로 남음.

## 13-3. 개인 액션 확인 → 추적 순환

1. 이하윤이 `/app/my/actions`(타임라인)에서 자기 액션 확인 → 상세에서 세부 내용·출처 회의·상위 팀 액션·프로젝트 태그 확인(모두 클릭 가능 링크).
2. 프로젝트 태그 클릭 → 프로젝트 상세 통합 타임라인에서 마케팅·디자인팀 팀 액션까지 확인 → 다른 팀 액션 클릭 → 그 팀 개인 액션 타임라인으로 내려감. 이 순환이 Z의 핵심 UX.

## 13-4. 인수인계서 — 이하윤의 휴직

1. 이하윤이 `/app/handover`에서 "휴직" 선택, 기간·액션 선택 → [생성].
2. 김서준이 `/team/handover/{id}`에서 타임라인 확인 후 "배정할 액션" 목록에서 각 액션의 담당자를 `<Select>`로 지정 → [인수인계 확정](중간 승인 자동). (휴직이라 PDF 다운로드는 없다 — 오프보딩 전용)
3. 박대표가 사원 상세에서 "김서준 중간 승인 완료"만 보고 **최종 승인**.

> 김서준(팀장 본인) 휴직이면: 본인이 개인 액션마다 팀원 재할당까지 지정해 신청 → `/team/handover` 없이 박대표가 조회만 후 [휴직 최종 승인]. 김서준 오프보딩이면: 박대표 최종 승인 후 인수인계서 "귀속 대기" → 새 개발팀장 지정 후 `/owner/leader-handovers`에서 귀속. 이 기간에도 "앱 개발 착수" 등 개발팀 팀 액션은 그대로 유지.
